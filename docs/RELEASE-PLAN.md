# Web 与微信小游戏发布计划

更新：2026-10-25。首发范围以现有第一幕「阴路夜巡」为基础，目标平台已确定为 **Web 与正式微信小游戏**。采用一套规则和配置、两个表现端；现有 Web 界面继续使用，微信端建设适配小游戏环境的界面与平台接口。

当前已具备第一幕游戏闭环，主要缺口集中在资源体积、发布流程、微信界面适配和完整试玩验证。微信工程、双端适配与线上发布尚未完成。当前优先实施拖牌目标反馈，其余工作按下述阶段推进。

## 当前基础

| 范围 | 现状 |
| --- | --- |
| 游戏闭环 | 地图、战斗、事件、商店、休息、奖励、首领胜败与局外成长已实现；第一幕 16 层，当前开放一个模式。 |
| 内容与规则 | `game/content/` 有 101 条卡牌、25 种敌人和第一幕配置；`game/src/runtime/` 通过通用规则执行效果并输出状态与事件。 |
| Web 界面 | `game/src/main.js`、视图模块和 CSS 使用 DOM、浏览器输入及音频接口；入口和主要资源使用相对路径。 |
| 静态构建 | `npm run build` 生成 `.local/dist/`，包含入口、运行源码与 `public/`；运行不依赖 Node 服务、配置工具或本地测试。 |
| 存档 | 当前为 `version:4 / ruleset:config-v1`，新局固定规则快照；进度保存在当前浏览器来源，已有写入失败提示与无效局内存档保留提示。 |
| 配置工具 | `tools/content-editor/` 可编辑卡牌、怪物、关卡相关源表，并使用正式规则预览；法器和药物尚未完全配置化。 |

玩法、架构与工具的具体边界分别见 `README.md`、[架构说明](ARCHITECTURE-V05.md)和[配置工坊](CONTENT-EDITOR.md)。

## 发布前的主要缺口

| 优先级 | 问题与影响 | 处理方向与完成条件 |
| --- | --- | --- |
| 高 | **资源体积过大。** 2026-10-25 的静态产物共 265 个文件、355.06 MiB；101 张专属卡图约 201.93 MiB，仅用于溯源的 21 张原件约 31.09 MiB。`tools/build.mjs` 当前原样复制素材。完整产物体积不等于首屏下载量。 | 保留来源原件，发布构建生成适合显示尺寸的派生资源；筛选发布文件、压缩图片、按需加载并规划分包或远程资源。分别测量首屏下载、解码内存、缓存占用和后续场景加载。 |
| 高 | **发布链路缺失。** 审查时本地没有 Git 远端和 `.github/` 工作流，部分必要源码与新素材仍未跟踪。 | 确定目标仓库、分支和源码公开范围，核对完整文件集合；从干净环境构建，通过发布前检查后生成可追溯的版本与产物。 |
| 高 | **微信运行工程缺失。** 当前没有小游戏入口、工程配置或平台适配层，DOM 界面无法直接运行。 | 完成小游戏渲染方案验证、平台接口和独立构建；先跑通一场真实规则战斗，再迁移全部界面。 |
| 高 | **完整冒险与手机验证不足。** 尚未完成正常数值下的完整 16 层浏览器通关，物理手机触控、安全区、后台恢复也未验收。 | 覆盖正常胜败、三种首领与续玩路径，记录实际难度和局时；随后分别验证 iOS、Android 的目标浏览器与微信真机。 |
| 中 | **缓存与更新方案缺失。** 当前模块、图片使用固定文件名，本地服务的 `no-cache` 行为不能证明生产更新的一致性。 | 为模块、资源和内容建立版本关联，验证新版本更新、旧页面驻留、资源缓存失效及回滚；避免混用不一致的模块和素材。 |
| 中 | **存档局限于当前来源。** 本地地址迁移至线上或更换设备时不会自动继承进度，没有导出、导入或云同步入口。 | 首发明确本机保存边界，设计可校验的备份与恢复；区分局内与局外记录，处理损坏和不支持的格式提示。继续遵守不兼容旧存档的项目约定，云同步后置。 |
| 中 | **干净环境无法重现完整回归。** `.local/tests/` 全部被 Git 忽略；`npm test` 缺少测试文件时会失败。 | 明确 CI 如何获得受控测试来源并恢复至 `.local/tests/`。构建与配置检查可独立执行，但不能宣称其等同于完整规则回归，也不擅自把本地测试移回正式源码。 |
| 中 | **平台生命周期未统一处理。** 当前直接使用 `localStorage`、浏览器音频和 Pointer Events；失焦取消拖牌已有处理。 | 统一输入、保存、音频暂停与恢复、前后台切换和资源请求；验证切回后既不丢进度，也不重复结算或残留拖拽状态。 |
| 中 | **首次操作引导不足。** 目前主要依靠静态小册与手牌提示；怪物意图只在详情展示，需要明确告知玩家点击查看。 | 增加简短首次引导，覆盖点怪看意图、点牌看详情、攻击上拖、自身牌下拖、借火与还愿；保持战场常态不展示意图。 |
| 中 | **试玩反馈不便复现。** 永久历史已有胜负、层数、战斗、还债和难度，尚无完整的种子、局时、内容版本及失败原因摘要。 | 增加可导出的本地试玩摘要，便于复现问题和比较平衡调整；先确定记录内容，再决定是否需要线上反馈服务。 |
| 后续 | **道具配置与内容扩展。** 法器、药物仍在 `game/src/runtime/items.js` 及运行时分支中维护；第二幕、百鬼试炼和长夜无尽尚未开放。 | 法器与药物逐步纳入通用配置和编辑器；第二幕与新模式安排在首幕首发之后。 |

## 双端共用边界

小游戏与浏览器使用不同的宿主接口。微信小游戏没有浏览器的 DOM、BOM；现有 HTML 与 CSS 需要迁移为小游戏可用的渲染实现，无法只增加上传脚本完成适配。渲染方案在单场战斗验证阶段确定，暂不指定引擎。[微信运行环境说明](https://developers.weixin.qq.com/minigame/dev/guide/game-engine/cocos-laya-egret.html)

| 部分 | 共用或适配方式 |
| --- | --- |
| 内容与规则 | 共用 `game/content/`、编译后的配置、规则解释器、种子随机、目标资格、存档结构和局外成长；不另建一套微信战斗规则。 |
| 规则结果 | 两端均提交动作并消费相同的状态与事件；动画回调不结算伤害或推进回合。 |
| 界面与动画 | Web 沿用当前视图；小游戏使用 Canvas／WebGL 或已适配小游戏的渲染方案，重现卡牌、战场、地图与菜单。 |
| 存储 | 平台层提供读取、写入、删除和错误结果；Web 对接浏览器存储，小游戏对接微信存储接口。双端共用格式不代表自动跨端同步。 |
| 输入与屏幕 | 统一点击、拖拽、取消与目标命中含义；分别适配触摸、鼠标、安全区、屏幕尺寸和微信界面遮挡。 |
| 音频与生命周期 | 平台层负责用户交互后启用音频、进入后台、回到前台、暂停与恢复；界面据此清理临时交互并恢复展示。 |
| 资源 | 共用有来源的美术，按目标端生成派生资源和清单；处理预加载、远程下载、缓存、失败重试与资源版本。 |
| 开发与输出 | 游戏本体仍属于 `game/`，工具属于 `tools/`，命令从根 `package.json` 进入；测试、证据、产物和临时文件继续位于 `.local/`。双端构建输出应分开，避免相互覆盖。 |

## 当前体验任务

拖拽作用于怪物的卡牌时，用目标反馈帮助玩家判断施放对象。Web 端已完成实现、本地自动检查及浏览器交互验证，具体结果记录在 `docs/DEVELOPMENT-V05.md`；小游戏端随界面迁移接入。

- 可作用的存活怪物头顶显示箭头；卡牌悬停在有效目标上时立绘泛白，怪物及箭头不缩放。
- 当前无法作为该牌目标的怪物不显示箭头，并变暗；反馈与实际出牌使用同一目标资格判定。
- 自身牌等没有敌方目标的牌使怪物变暗，同时保留自身施放引导；群体牌按其作用范围提示。取消、无效松手、施放完成或页面失焦后清除提示。
- 护甲、减伤或一次效果被阻挡不自动等同于不可选中。后续新增禁选规则时，由通用规则接口决定资格，界面不按牌名或怪物名另写分支。
- 当前没有新增逐怪免疫玩法；后续若增加群体／随机牌的部分禁选或免疫，实际效果目标解析也需复用同一规则，保证提示与结算一致。
- 验收覆盖单怪、多怪、不可用目标、群体牌、自身牌与取消流程，并检查箭头不遮挡血条和关键操作。

## 分阶段实施与验收

### 第一阶段 双端单场战斗

先建立小游戏最小工程与平台接口，以现有规则完成一场战斗。验证牌面、拖拽、选敌、怪物行动、动画和保存恢复，再扩大迁移范围。

完成条件：同一配置、种子与动作序列在两端得到一致的规则状态、随机状态和事件顺序；非法目标不扣费、不消耗卡牌；后台恢复与动画中断不会重复结算。小游戏开发者工具预览与真机表现分别记录。

### 第二阶段 完整界面与资源优化

迁移主页、模式与行装、地图、商店、事件、休息、奖励、图鉴和结算。建立保留原件、按端生成发布资源的工具链，并以实际设备测量制定加载和内存预算。

微信官方在 2026-10-25 的文档限制为主包不超过 4M、主包与分包总计不超过 30M。按实际上传工程检查包体；分包、远程资源、缓存和弱网重试必须一起设计。[代码包限制](https://developers.weixin.qq.com/minigame/dev/guide/base-ability/code-package.html)、[分包加载](https://developers.weixin.qq.com/minigame/dev/guide/base-ability/subPackage/useSubPackage.html)

完成条件：所有第一幕流程可使用，来源原件完整保留，发布资源引用无缺失；测得首屏与场景切换流量、加载时间和内存表现，断网或下载失败时有可理解的处理。

### 第三阶段 Web 试玩发布

确定 GitHub 目标仓库、Pages 来源和部署分支，通过 Actions 构建并发布 Web 产物。配置工具、QA 夹具、本地测试和历史归档不进入站点；发布前解决干净 CI 的测试来源。

GitHub Pages 支持通过自定义 Actions 工作流构建并部署静态产物，可直接使用构建目录作为发布输入。[GitHub Pages 官方流程](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)

完成条件：干净环境构建成功；仓库子路径、HTTPS、刷新、资源与版本更新正常；存档保存和恢复通过线上来源验证；保留版本标识、可用产物和回滚步骤。

### 第四阶段 微信真机与提审

补齐小游戏账号与 AppID、开发者工具工程配置、资源托管、网络域名、介绍与截图等发布材料。按实际账号主体、类目及届时平台要求核对提审材料，平台能力按需要逐项接入。

完成条件：iOS 与 Android 微信真机完成正常第一幕胜败、续玩和后台恢复；弱网、资源加载失败、安全区、拖牌与音频行为符合预期。体验版验证完成后再提交审核，审核结果与正式发布状态单独记录。

分享、登录、排行榜等微信能力通过平台接口接入，不作为首幕规则运行的依赖。Git 提交、推送及正式发布按 `AGENTS.md` 的明确授权要求执行。

| 验证层级 | 本计划要求 |

| 自动检查 | 配置、素材、构建、规则、目标资格、确定性与保存恢复；发布环境可以重现。 |
